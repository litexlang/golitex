## Negative integer powers: a calculation gap

```litex
2^(-3) = 1 / 8
```

The direct assertion rejects at `search_proof`. Independently,
`eval 2^(-3)` fails at `eval`; the attempted reciprocal identity
`2^(-3) = 1 / (2^3)` also rejects. The positive power and its reciprocal
`1 / (2^3) = 1 / 8` do verify.

The exact rational path in `src/rational_expression/exact_rational.rs` converts
the exponent to a nonnegative integer. The decimal path in
`decimal_arithmetic.rs` likewise rejects negative exponents. This is stronger
evidence than a failed direct proof alone.

Category: proposed local Rust semantic repair. Next action: add checked exact
reciprocal evaluation for integral negative powers of a proved nonzero numeric
base, retaining overflow/resource and zero-base rejection. Generalized
real/complex exponent semantics or representation changes need discussion.
No implementation is made in this audit.

## Fractions: exact inequality does not yet give exact order

```litex
1 / 3 <= 1 / 2
min(1 / 3, 1 / 2) = 1 / 3
```

Both direct statements reject at proof search. This explicit proof succeeds
in full, without trust:

```litex
1 / 3 = 2 / 6
1 / 2 = 3 / 6
2 / 6 <= 3 / 6
1 / 3 <= 1 / 2
min(1 / 3, 1 / 2) = 1 / 3
```

The closed numeric `<=` leaf in
`verify_atomic_except_equality/.../less_equal.rs` uses normalized decimal
comparison, while `1/3` has no terminating decimal value. Exact rational
inequality exists, but that is a different consumer. The source inspection and
checked common-denominator route support this diagnosis; the `max` fixture
also still rejects, but a separate explicit `max` route was not verified.

Category: Litex authoring improvement; a local exact-order leaf repair is a
candidate. Next action: retain the verified proof route, and investigate exact
rational comparison with equal-value, sign and overflow controls if direct
automation is wanted. General symbolic inequality search needs discussion.

## Function composition: eval succeeds; the direct proof needs a consumer

```litex
have fn f(x R) R = x + 1
f(f(1)) = 3
```

The direct equality rejects at proof search. `eval f(f(1))` returns `3` and
stores no equation. This explicit equality chain verifies:

```litex
have fn f(x R) R = x + 1
f(1) = 2
f(2) = 3
f(f(1)) = f(2) = 3
```

The evaluator already retains function-application evidence. The numeric
equality consumer in `search_equal_fact_by_aggregate_calculation.rs` enters only
when it detects an aggregate, so it does not automatically cover plain function
composition. A captured anonymous function likewise evaluates to the expected
value while its direct equality fixture rejects.

Category: Litex authoring improvement. A bounded equality consumer for checked
function evaluation could improve direct automation, while keeping `eval`
free of stored equations. Changes to global recursion, search or storage need
discussion.

There is a separate, less well diagnosed boundary:

```litex
have fn f(x R) fn(y R) R = fn(y R) R {x + y}
f(2)(3) = 5
```

Here the declaration succeeds, but both the equality and `eval f(2)(3)` fail.
The next owner is checked expansion of the function-valued inner application
and binder substitution. Category: provisional, diagnosing; the successful
simple composition route does not establish a curried repair.

## Sets: explicit proof commands already cover some direct failures

```litex
{1, 2} = {2, 1}
```

The direct assertion rejects; this command succeeds:

```litex
by extension {1, 2} = {2, 1}
```

Similarly, direct `{1} != {2}` rejects, but this explicit proof succeeds:

```litex
not 1 $in {2}
by contra:
    ? {1} != {2}
    1 $in {1}
    1 $in {2}
    impossible 1 $in {2}
```

The nested displayed-set fixture `{1} $in {{1}, {2}}` still rejects during WD
because pairwise distinctness is required. This audit establishes a way to
prove the distinctness lemma; it does not claim the unchanged nested fixture
or every set/family operator now passes.

Category: Litex authoring improvement. Use the checked commands; an automatic
logical shortcut is not required to establish mathematical availability.
Before considering a WD change, check the actual nested goal after the lemma.
Global extensional search or container representation changes need discussion.

## Shapes: an intermediate equality works; the alias fixture used a builtin name

```litex
((1, 2), 3)[1][2] = 2
```

The direct assertion fails during WD of the intermediate projection. This
two-step proof succeeds:

```litex
((1, 2), 3)[1] = (1, 2)
((1, 2), 3)[1][2] = 2
```

The separate recorded alias attempt rejects:

```litex
let C = cart(R, Z)
cart_dim(C) = 2
```

Its WD requirement `$is_cart(C)` also fails in isolation. The initial audit
incorrectly attributed this to alias shape transport. `C` is parsed as the
builtin complex set, rather than the newly bound name. The intended ordinary
alias succeeds with all its existing properties:

```litex
let product_space = cart(R, Z)
$is_cart(product_space)
cart_dim(product_space) = 2
```

The equality is already in `SpecialProperty::Equality`, and the existing
`infer_equal_fact/cart_tuple_shape.rs` derives shape and dimension. The
[correction note](experience/problem_notes/cart_alias_name_correction_2026-10-03.md)
and [journal](proof_journals/cart_name_correction_2026-10-03.json) retain the
current successful build, ordinary/typed aliases and negative controls.

Category: authoring improvement for the projection and fixture naming
correction for the alias. No new alias state is justified by this reproduction.
The original direct nested projection `eval` also fails in the scan snapshot;
the successful proof chain does not certify that direct eval path.

## Trigonometry and complex modulus: prerequisites and value proofs differ

```litex
tan(pi) = 0
log(e, e) = 1
C_abs(3 + 4 * i) = 5
```

The first statement initially fails WD on `cos(pi) != 0`. Both
`cos(pi) = -1` and `cos(pi) != 0` verify, but the subsequent `tan(pi) = 0`
still rejects at proof search. A nonzero rule alone would not close this case.

The logarithm fails WD on `e != 1`. Attempts to prove `e > 1` and `e != 1`
also fail. No logarithm-value repair has been established here.

For the modulus, `re(3 + 4*i) = 3` and `img(3 + 4*i) = 4` both verify;
the defining magnitude-to-sqrt identity and `C_abs(3 + 4*i) = 5` do not.
The owning WD entrances and `by_trig_complex_identities.rs` support parts of
these families; these failures do not establish that the entire families are
absent.

Category: provisional, diagnosing. Trace each existing defining identity and
proof route separately before proposing local rules. New public mathematical
contracts or broad identity/search policies need discussion.

## Struct fields: mapping contract still needs diagnosis

```litex
struct Point:
    x R
    y R
have p &Point = (1, 2)
p.x = 1
```

The declaration succeeds but the field equality rejects at proof search.
An attempted `have p &Point = &Point{1, 2}` instead hits intentionally removed
explicit struct selection syntax; it is not a proposed solution.

Category: provisional, diagnosing. Trace the existing tuple-backed default
view and field evidence before assuming a representation change or adding a
rule. An unsettled tuple-to-field public contract needs discussion; protected
Obj/Stmt/Fact layout changes require explicit authorization.
