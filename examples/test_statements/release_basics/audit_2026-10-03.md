## 需要强化写法的语句语料

原来的倒计时例子直接要求：

```litex
f(1) = 0
```

冻结版本中该直接推导失败；下面明确链通过：

```litex
f(0) = 0
f(1) = f(1 - 1) = f(0) = 0
f(2) = f(2 - 1) = f(1) = 0
```

相应 have-fn、algo 和模板的完整文件强化变体已经执行。模板需要先明确证明 `\template_count<R>(0) = 0`，再写完整链。对应来源和全部尝试保留在 `proof_journals/authoring-files.json`。这属于类别 1：Litex 写法可强化。没有因此要求更强的自动展开，也没有修改原语料期待或把错误接受成通过。原始 377 项结果与强化变体结果分别报告。

## 其余失败与测试预期漂移

36 个 Rust library 失败及 1 个 integration 失败逐项保留在 `proof_journals/kernel_failures.json`，每项有原 Rust 测试、原失败输出、owner 与下一步。33 个 Obj 独立失败按对象归档。部分是已知 gap 或现有显式接口边界，部分尚需定位最早失败原因。

例如：

```litex
eval sqrt(0.36)
eval sqrt(2)
```

实际分别返回 `3 / 5` 与 `sqrt (2)`，而旧测试要求前者必须是 decimal Number `0.6`、后者必须失败。前者数学值相同；这些是表示/公共返回契约的预期复核，不能直接叫数学 bug。`fn(x R) x` 之类旧正例又涉及当前明确拒绝的函数依赖签名，不能为迁就旧用例扩展 AST/签名。相关责任目录记录已经注明。

最初遇到的最小 predecessor/归纳 WD 和 nested positive-natural aggregate InternalBug，在最后快照的直接补查中通过。它们由并行源码更新后恢复；本任务没有修改 Rust 或确认具体修复因果。历史记录仍保留，避免误报为本轮仍在的问题。
