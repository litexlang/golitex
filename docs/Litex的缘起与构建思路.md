# Litex 的缘起与构建思路

官网页面: https://litexlang.com/doc/Litex的缘起与构建思路

英文版: https://litexlang.com/doc/Motivation_and_Construction_Thinking_Behind_Litex

我想从第一性原理重新思考数学与代码的关系——并由此重新思考：数学是什么，证明又意味着什么。Litex 正是从这份好奇里长出来的。

第一个问题是：如何在自然语言的自由与形式数学的严谨之间找到平衡。自然语言为直觉与隐含联系留出空间；形式语言则必须把这些联系写到机器足以检查的精度。我希望有一种语言，既能保留阅读数学的体验，又能承担起检查数学的责任。

我的答案，首先是选择合适的基础，以及刚刚够用的内置数学对象与陈述。一小套熟悉的词汇，让人第一眼需要学的东西更少；也意味着语言必须解释并实现的、彼此交互的概念更少。挑战在于：词汇要小到容易把握，又要表达力足够，能在其上继续建造。

集合论感觉是自然的基础。集合、元素、函数与关系，本来就属于许多人理解数学的方式。由此出发，我希望把人们在 LaTeX 里惯常写下的数学符号带进语言，连同它们背后的数学关系一并纳入。认出一个交集符号只是开始；系统还需要理解交集如何与属于、包含、相等相联系。

数学词汇就位之后，下一个问题是怎么写。我选择了类似 Python 的语法：缩进、可见的结构、相对较少的标点。更重要的是，我希望用户写下他们想建立的数学陈述，而由内核为每一步找到局部的正当理由。作者提供数学路线；系统处理那些让这条路线可被检查的常规连接。

这一选择塑造了验证引擎。在典型的 tactic 工作流里，作者给出构造证明的指令，最终由内核检查。Litex 把“下一条数学事实”放在交互的中心：给定当前上下文，系统能否为这个陈述辩护？这是关于默认写作体验的选择；其他证明助手也提供声明式界面与自动化。Lean 的文档说明了它自己的 elaboration 与检查模型。

我最早实现这一想法的方式很简单：匹配与代换。找到相关的已知事实，与正在检查的陈述做匹配，再判断所需的代换与条件是否成立。这个想法后来发展成：结构化的事实查找、有界递归验证、内置数学规则，以及引入见证或分情形等显式的证明步骤陈述。

工程上很大一部分，在于组织知识，使正确的事实能被找到并使用。我把 Litex 的这一部分想成一个专为数学推理设计的数据库：它的存储与查找机制理解数学结构、作用域，以及事实适用的条件。实现在 golitex 源码里；网站上的 How Litex Works 可视化则提供了另一种探索设计的方式。

但检查一条陈述，只是我想要的一部分。我还希望系统返回对验证过程的解释：它用了哪些事实、哪些规则把它们连起来、哪一步无法被辩护。若 Litex 要帮助人们理解数学，它的推理就必须成为人们可以检视的东西。

一旦验证产出结构化的记录，进一步的可能就出现了。定义与已建立事实之间的关系可以支撑知识图谱；解释可以成为交互式数学习题书的一部分；AI agent 可以用反馈修正失败的一步，并从已接受的知识继续。围绕这种交互构建一个有能力的数学 agent，是我更长远的目标之一。

同一份记录也为通往 Lean 的桥梁提供了基础。编译器可以同时利用 Litex 源码及其验证结果，按 Litex 实际使用的推理生成 Lean 陈述与证明。对已支持的翻译路径，Lean 可以再独立检查生成的证明。覆盖范围与忠实翻译，仍需一条路线一条路线地建立。

我看到这种连接有巨大价值。它给 Litex 一条进入 Lean 生态的路径，并为翻译后的证明增加一层独立检查。它也打开了这样的可能：Litex 作为更易接近的前端，让人们用更熟悉的写作风格为形式数学做贡献。

作为一名黑客，我一直在通过建造我能用的东西、检视它做了什么、让每一个答案暴露下一个问题，来探索这些问题。这个过程仍在改变我对数学、代码与证明的看法。

我相信，在 AI 时代，数学会变得更加重要。我的梦想是：形式推理能在数学被使用的任何地方变得可接近——并且更多人能够理解、质疑、并贡献于我们共同建造的知识。

Litex 仍在快速开发中。我希望它能更快地帮助实现这个梦想。
