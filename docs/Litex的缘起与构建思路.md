# Litex 的缘起与构建思路

Jiachen Shen, 2026.10.21

官网页面: https://litexlang.com/doc/Litex的缘起与构建思路

英文版: https://litexlang.com/doc/Motivation_and_Construction_Thinking_Behind_Litex

Litex围绕这样的想法展开：能不能写下数学，直接得到形式化代码？ 从小我们就知道数学是一种严格的语言，每一句话都能找到相应的佐证来支撑它的正确性。那既然数学本身就是一个严格的语言，为什么不能让数学本身成为一种形式化语言？或者设计一个形式化语言，它在书写上就和日常数学差不多，只是添加一些合理的约束就应该确保其足够结构化，方便去机械地做证明。

这是从第一性原理重新思考数学、自然语言与代码的关系——并由此重新思考：数学是什么，证明又意味着什么。Litex 正是从这份好奇里长出来的。它想让数学本身成为一种形式化语言。这样一来，任何使用数学的人，不论是中小学生还是AI工程师，不用经过专业学习，都直接有了使用形式化工具的能力。

下面是Litex的设计上的思考。

第一个问题是：选择合适的数学公理基础。任何形式化语言都依赖特定的数学公理，不同公理体系的选择直接影响了这门语言是什么样的。先比较目前最常用的形式化语言Lean。Lean选择类型论，这是一种抽象且自洽的数学公理体系，强大且可编程。但它和日常数学有不可逾越的的区别。比如，Lean/Mathlib为了让函数是全函数，故意让 `1/0 = 0`, `1 - 2 = 0`。这样的设计有时会让人们以为自己用形式化语言证明了A，但事实上证明的东西是和A有一些区别的B，因为常见的数学符号在Lean可能有其他意思。这让形式化工具的使用和学习门槛对普通人而言遥不可及。

为了让更多人学会并使用Litex，Litex选择集合论作为它的基础。集合、元素、函数与关系，本来就属于许多人理解数学的方式。这些基本的术语从中学时代就伴随我们直到上班工作。由此出发，我希望把人们在 LaTeX 里惯常写下的数学符号带进语言，连同它们背后的数学关系一并纳入。认出一个交集符号只是开始；系统还需要理解交集如何与属于、包含、相等相联系。在这里，`1 / 0`是会因为不满足良定义性而报错，而`1 - 2 = -1`。

数学词汇就位之后，下一个问题是设计语法。我要让数学语言直接就成为形式化代码。诸如`1 + 1 = 2`, `forall x, y R: x >= 0 and y >= 0 => x + y >= 0` 这样的语句，在Litex中是直接能运行的。更复杂的数学语句的组织方式类似Python的语法。用户直接写要证明什么，Litex负责帮你告诉你这句话为什么成立或不成立。当你输入`1 + 1 = 2`，Litex会返回

```
{
  "statement_result": "accepted",
  "statement": "(1 + 1) = 2",
  "proof_method": {
    "type": "by_closed_calculation",
    "rule_name": "Closed calculation",
    "message": "Exact evaluation of closed expressions without proof search"
  },
  "stores": [
    "(1 + 1) = 2"
  ],
  "infers": []
}
```

这样的好处是，Litex的源代码非常整洁和清晰。用户一目了然知道自己在证明什么，已经证明了什么。Litex的输出告诉你为什么每句话是正确或不正确的。阅读和书写Litex源码就有希望像写日常数学那样直接。

这一选择塑造了验证引擎。在典型的 tactic 工作流里，作者给出构造证明的指令，最终由内核检查。Litex 把“下一条数学事实”放在交互的中心：给定当前上下文，系统能否为这个陈述辩护？这是关于默认写作体验的选择；其他证明助手也提供声明式界面与自动化。Lean 的文档说明了它自己的 elaboration 与检查模型。

我最早实现这一想法的方式很简单：匹配与代换。找到相关的已知事实，与正在检查的陈述做匹配，再判断所需的代换与条件是否成立。这个想法后来发展成：结构化的事实查找、有界递归验证、内置数学规则，以及引入见证或分情形等显式的证明步骤陈述。

工程上很大一部分，在于组织知识，使正确的事实能被找到并使用。我把 Litex 的这一部分想成一个专为数学推理设计的数据库：它的存储与查找机制理解数学结构、作用域，以及事实适用的条件。

但检查一条陈述，只是我想要的一部分。我还希望系统返回对验证过程的解释：它用了哪些事实、哪些规则把它们连起来、哪一步无法被辩护。所以Litex有一个数学特化的搜索引擎，专门在这个为数学特化的数据库结构上工作，能自动基于上下文和Litex内置的数学推理规则，识别和判定每一个数学语句成立与否。

litex能把常见的数学表达一步步解析成机器可识别可存储可调用的数学知识，是很难的，这个功能是Litex项目的核心，也是Litex多达20多万行Rust源代码的内核所做的。因为前人没有类似这样的工作，所以这个数学特化的数据库和搜索引擎完全由Litex发明人自行开发。好处是，我已经开发好了，这整个流程不只是能做验证，它甚至还能输出结果，告诉你为什么这些数学语句能成立。这对数学教育也是有帮助的：我们可以构建可交互的数学书，数学书是以类似自然语言的Litex源码格式出现的，每句Litex语句都能对应一个它”为什么成立“的结构化信息。所有的结构化信息连起来，就成了一张网，教会大家数学概念之间是怎么互相链接起来的。这个过程可能会改变读者对数学、代码与证明的看法。

一旦验证产出结构化的记录，进一步的可能就出现了。定义与已建立事实之间的关系可以支撑知识图谱；AI agent 可以用反馈修正失败的一步，并从已接受的知识继续。围绕这种交互构建一个有能力的数学 agent，是我更长远的目标之一。

同一份记录也为通往 Lean 的桥梁提供了基础。编译器可以同时利用 Litex 源码及其验证结果，按 Litex 实际使用的推理生成 Lean 陈述与证明。对已支持的翻译路径，Lean 可以再独立检查生成的证明。覆盖范围与忠实翻译，仍需一条路线一条路线地建立。有人会问，Litex源码这么多，是不是有Bug，有Bug是不是说明不严格？Litex当然会有bug，但Litex代码能编译到Lean，如果编译成的Lean能通过，那事实上Litex源码就是成立的了，所以用户们也不用太担心Litex的严格性问题。

Litex能编译到Lean有巨大价值。它给 Litex 一条进入 Lean 生态的路径，并为翻译后的证明增加一层独立检查。Lean一直以难以被阅读著称，它的语义和标准数学语义也有一些冲突。Litex相当于提供了门槛更低的，让普通人使用形式化工具的一种途径。

虽然可能做数学研究的评价体系受到了AI冲击，但我觉得现在是学习数学的最好的时候。普通人不需要做数学，他们只需要使用数学，把数学当做他们理解世界的工具。AI并没有促进人们理解数学，在帮人学习上，本质上还是一种电子化的做题家老师。但AI让Litex这样的项目得以快速实现，Litex从第一性原理上，重新审视了什么是数学，什么是推理这样的问题。希望学习过Litex的读者，未来看到自然语言写的数学，也能联想到Litex，联想到数学本身也是一个严格的语言，它有它背后的逻辑和脉络。我想就够了。
