## Litex 蓝图总览

AI 正在迅速降低生成推理过程、数学证明和科研发现的成本。人和 AI 可以在短时间内给出大量看似合理的论证，但“像是正确”不等于“已经通过检查”。我们正在进入一个 **推理过剩、验证危机** 的阶段：候选智力产出越来越多，能够被可靠验证的部分却没有同步增长。

教育、科研、工程和 AI 审核因此出现新的形式化需求。要让这些场景真正发展，形式化不能只是专家工具；已经懂相关数学的人也必须能参与表达和审核。

先看最简单的事实。蓝图主要以Lean为参照物来表现Litex的特点。

Litex：

```litex
1 + 1 = 2
```

Lean：

```lean
import Mathlib

example : (1 : ℝ) + 1 = 2 := by norm_num
```

一个已经理解 `1 + 1 = 2` 的三岁孩子，不应先学习 `norm_num` 才能把它形式化。验证指令可以帮助专家，但不应成为表达数学的入场券。

这种差别也出现在函数的良定义性上。对于定义域为正实数的函数，Lean 的一种常见编码是：

```lean
example
    (f : {x : ℝ // x > 0} → ℝ)
    (x : ℝ) (hx : x > 0) :
    f ⟨x, hx⟩ = f ⟨x, hx⟩ := rfl
```

对应的 Litex 是：

```litex
forall f fn(t R: t > 0) R, x R:
    x > 0
    =>:
        f(x) = f(x)
```

**这是一个再直白不过的事实：函数值等于自身。** 我们证明任何定义域在正实数域的函数，它的函数值等于自己。

但在上面的 Lean subtype 编码中，调用 `f` 时不仅要传入 `x`，还要把证明 `hx : x > 0` 打包成 `⟨x, hx⟩`，写成 `f ⟨x, hx⟩`。

这与通常的函数写法很不一样：函数接收自变量，而不是良定义性证书。Litex 仍然严格检查 `x > 0`，但源码只写 `f(x)`。

> **用户写数学，系统管理验证证据。条件不能省略，证书不必手传。**

这不是降低验证标准，而是降低工具门槛。好的数学符号一直在吸收机械细节，让人专注于数学；AI 时代的形式化语言也需要这样的抽象层。

Litex 检验这样一个假设：能否在不降低验证标准的前提下，降低形式化门槛，让学生、领域专家和 AI 更容易生产机器可检查的数学。

这条尝试的路径是：

*Litex 是一门基于集合论、事实导向、自下而上构建证明流、与 Lean 兼容的形式化语言。它让人类和 AI 直接写下数学事实，并看见验证为何成功、在何处停止。*

1. 基于集合论：Litex 以 ZFC 集合论为基础，让数学对象统一通过集合和成员关系来组织；同一个对象可以属于多个集合；数学对象与关于对象的事实在语言中分开表示。作为对比，Lean 的集合 `Set α` 则先依赖更抽象的载体类型 `α : Type*`；数学对象和命题都由类型系统组织，这种方式具有很强的泛化性。Litex 的取舍则是要让表达集合论及其上的常见数学知识更为清晰。
2. 事实导向：Litex 源码主要写“什么数学事实应当成立”，内核根据事实的谓词和参数，从内置规则、已证明事实和等式匹配中寻找验证方式；对象与表达式的良定义性，也会在事实被接受前自动检查。作为对比，典型的 Lean 证明指令（tactic）源码主要写“下一步怎样处理证明目标（Goal）”，信息视图（Infoview）则显示操作之后还剩什么证明目标。Lean 的类型系统同样会检查表达式是否类型正确；所需的类型信息、类型类实例和证明前提，则通过显式或隐式参数进入表达式与定理接口。
3. 自下而上构建证明流：数学证明既可以从已知条件出发，不断得到新事实并最终汇聚到结论；也可以从最终证明目标出发，把它反向化约成已知条件。Litex 默认采用前一种、让上下文随已验证事实向前生长的工作流；Lean 常见的证明指令交互通常采用后一种。两者都不把另一种方向排除在表达能力之外。
4. 和 Lean 兼容：Litex-to-Lean 编译器的目标，是把内核已经找到的验证路径翻译成 Lean 证明对象，再由 Lean 内核独立检查。当前编译器只覆盖部分验证路径；“所有 Litex 源码都能编译成 Lean”是尚未完成的方向，不是测试版已经达成的能力。

两种流程可以简化成：

```text
Lean：命题 → 证明目标 → 证明指令与细化 → 证明对象 → 内核检查
Litex：对象和事实 → 内核检查并寻找依据 → 已验证事实扩展上下文
```

理想状态是，用户在使用 Litex 时，能够保持与进行非形式化数学时相同的心流：把注意力放在数学对象、条件、中间事实和结论上，而不必先面对证明助手底层的理论抽象、陌生的形式化语法或庞大的外部库。Litex 则像一位副驾驶式助手（copilot），在一旁提供快速、局部而可追踪的验证反馈。*希望 Litex 能让更多各行各业的非专业人士更容易进入形式化数学的世界。*

> **Lean 也支持其他编码和自动化方式；这里比较的是源码接口，而不是两种语言能否表达同一个命题。**

> **这是设计方向，不是对当前语言、标准库或编译器已经完备的声明。**

<details>
<summary><strong>基本术语：形式化语言、证明目标、证明指令与内核</strong></summary>

- **形式化语言（formal language）**：语法和含义由明确规则规定、因而可以被机器解析和检查的语言。“形式化”说的是表达规则具有精确含义，不是行文显得正式；形式化语言也不一定是通用编程语言。
- **证明助手（proof assistant）**：帮助用户表达证明、给出交互反馈，并由机器检查证明的软件。Lean 是一个具有通用编程能力的证明助手。
- **证明目标（Goal）与信息视图（Infoview）**：证明目标是当前等待证明的命题；信息视图是 Lean 编辑器中显示当前证明目标、局部变量和已知假设的窗口。
- **上下文（context）**：当前作用域内可使用的变量、定义、假设和已验证事实。加入一条新事实会扩展上下文，让后面的推理可以使用它。
- **证明指令（tactic）**：操作当前证明目标的命令，例如引入变量、按等式改写或把一个目标拆成若干子目标。证明指令描述“下一步怎样证明”，本身不是最终接受的证明对象。
- **证明对象（proof term）与细化（elaboration）**：证明对象是机器可以检查的完整证明；细化是系统补全源码中省略的信息，并把用户代码变成完整证明对象的过程。
- **内核（kernel）**：在 Lean 中，内核是按照基础规则核验证明对象的可信核心。证明指令可以很复杂，但其结果仍须通过内核检查；内核通常不负责替用户选择高层证明步骤。
- **内核/验证器（kernel/verifier）**：对“负责检查”的程序部分的宽泛称呼。Litex 内核不仅核验对象是否良好定义，还会从内置规则和当前上下文中寻找事实的验证依据，因此它不能直接等同于 Lean 的内核；Litex 的可信边界——也就是系统正确性所依赖、必须信任的部分——也相应更大。

</details>

<details>
<summary><strong>为什么 Litex 诞生在 AI 时代</strong></summary>

许多编程语言在早期由一个或少数设计者主导，最初的实现也常由设计者亲自完成。Litex 更难：它选择了与主流形式化语言不同的用户接口，许多地方没有现成答案；同时，我认为语言替用户承担得越多，用户使用起来就越自然，因此 Litex 的验证器内核有意承担了大量搜索、良定义性检查和证据管理工作。这是一个有意做得很大的内核。

在过去，我单独一个人几乎不可能独自完成语言设计、实现架构和大型验证器的长期维护；这种工作量很难由任何一个人承担。AI 改变了实现成本：当框架、语义和边界先被明确后，大模型往往能快速生成正确或接近正确的实现，再由测试、审查和反例筛掉错误。这让我可以把更多精力放在设计和验收上。AI 不是正确性的来源，但它让这种规模的个人语言项目第一次变得可行。

Litex-to-Lean 编译器提供另一层长期保障：目标是把 Litex 找到的验证路径编译成对应的 Lean 证明对象，再由 Lean 内核独立检查。当前编译器只覆盖部分路径；未来即使实现完整覆盖，也仍需审计 Litex 与 Lean 之间的语义对应。但当每个结果都能经过这条独立复核路径时，正确性就不必只依赖规模较大的 Litex 验证器。

</details>

## 总体交互闭环：直接写下事实，看见验证为何成功、在何处停止

当人类和 AI 都可以生成越来越多候选推理时，形式化语言不仅需要检查最终成品，还需要让每条已接受事实的依据和第一条尚无依据的事实变得可见。Litex 希望提供的总体交互闭环是：**人类或 AI 写下下一条数学事实，检查器返回接受它的依据；如果当前上下文还不足以支持它，检查器则指出验证停在了哪条事实。**

先看一个很小的集合包含例子：

```litex
forall A, B, c set, x A:
    A $subset B
    B $subset c
    =>:
        x $in B
        x $in c
```

源码直接写出两个应当成立的数学事实。当前发布版运行器（release runner）的结构化验证结果会记录每条事实和验证它的规则；下面只抽取与这个例子有关的关键字段：

```text
{
  "statement": "x $in B",
  "proof": {
    "kind": "BuiltinRule",
    "diagnostic_label": "membership through a known direct set inclusion"
  }
}
{
  "statement": "x $in c",
  "proof": {
    "kind": "BuiltinRule",
    "diagnostic_label": "membership through a known direct set inclusion"
  }
}
```

第一条结论由 `x $in A` 和 `A $subset B` 支持；它通过以后，`x $in B` 又成为第二条结论可以使用的事实，并和 `B $subset c` 一起支持 `x $in c`。这同时展示了两个层面：用户源码保存“什么数学事实应当成立”，验证结果保存“系统为什么接受它”。

如果再声明一个集合 `d`，却不给出任何把 `x` 或前述集合连接到 `d` 的条件，然后把 `x $in d` 加为第三条结论，当前运行器会返回 `UnknownError`，并在结构化结果中指出：

```text
"failed_prove": {
  "index": 3,
  "count": 3,
  "statement": "x $in d",
  "unknown_result": {
    "type": "atomic fact unknown",
    "goal": "x $in d"
  }
}
```

这里的 `unknown` 不表示 `x $in d` 为假，只表示当前上下文和当前验证能力没有建立它。对于这个包含三条结论的整体 `forall`，第三条失败会使外层语句整体不写入环境；在由多条独立陈述或事务式尝试组成的增量工作流中，先前已经接受的陈述则可以保留为已验证前缀。因而，“看见验证在何处停止”不应被理解成 Litex 已经解决了证明搜索，也不保证每次诊断都给出完整、最小的失败原因；它强调的是，成功依据和当前无法建立的具体事实都能成为下一轮修正可以读取的结构化反馈。

这给人类和 AI 提供了同一个循环：提出下一条事实，读取验证依据或停止位置，保留已经接受的进展，再从边界处继续。这个循环由四个设计支柱共同支撑：集合论决定用户直接面对什么对象，事实导向决定源码保存什么，自下而上的证明流决定已验证事实怎样继续生长，而 Lean 兼容则为当前已经覆盖的验证路径提供独立复核和生态出口。

<details>
<summary><strong>同一个例子：Lean 信息视图（Infoview）与 Litex 验证输出分别呈现什么</strong></summary>

在 Lean 中，同一个集合包含证明从最终目标 `x ∈ c` 开始，由证明指令逐步化约到已有假设：

```lean
import Mathlib

example {α : Type} {A B c : Set α}
    (hAB : A ⊆ B) (hBc : B ⊆ c)
    {x : α} (hx : x ∈ A) :
    x ∈ c := by
  apply hBc
  apply hAB
  exact hx
```

信息视图显示每次证明指令执行后剩下的证明目标：

```text
进入 `by` 后：
⊢ x ∈ c

`apply hBc` 后：
⊢ x ∈ B

`apply hAB` 后：
⊢ x ∈ A

`exact hx` 后：
no goals
```

信息视图清楚呈现“还需要证明什么”；Litex 的源码和运行器轨迹（runner trace）则同时保留“已经建立了哪些数学事实”“系统依据什么接受它们”，并在无法继续时把停止边界落到具体事实上。因此，Litex 的默认产物更接近一份可由人和 AI 直接阅读、检查、修正和续写的证明记录；这里比较的是默认工作流及其自然产物，并不意味着 Lean 不能书写前向证明或把中间结果保存下来。

</details>

## 1. 基于集合论：让集合论知识保持集合论的样子

如果形式语义既要精确，又要让数学使用者能够直接审核，第一项设计选择就是：用户在源码中首先面对什么样的数学对象？Litex 的答案是集合、成员关系和集合之间的关系。因此，当问题本身就是集合论问题时，用户可以直接写集合、子集和交集，不需要先引入一层承载这些集合的类型。

下面这段 Litex 代码声明了交集关于子集关系的单调性：

```litex
forall s, t, u set:
    s $subset t
    =>:
        intersect(s, u) $subset intersect(t, u)
```

这不是一个留待补全的证明空洞，而是交给内核检查的完整事实。这个事实的日常数学读法就是：取 `intersect(s, u)` 的任意成员 `x`，`x` 同时属于 `s` 和 `u`；由 `s $subset t` 可知 `x` 也属于 `t`，因而属于 `intersect(t, u)`。用户声明应当得到的数学结果，内核负责从交集成员的展开、成员关系沿子集的传递，以及右侧交集成员的重新组合中寻找验证路径。

下面是 Lean 版本的同一命题。示例出自 Lean 经典教科书《Mathematics in Lean》的集合论章节。

```lean
import Mathlib.Data.Set.Lattice

section
variable {α : Type*}
variable (s t u : Set α)
open Set

example (h : s ⊆ t) : s ∩ u ⊆ t ∩ u := by
  rw [subset_def, inter_def, inter_def]
  rw [subset_def] at h
  simp only [mem_setOf]
  rintro x ⟨xs, xu⟩
  exact ⟨h _ xs, xu⟩
end
```

这段 Lean 代码的第一层对象不是集合，而是 `α : Type*`：`s`、`t`、`u` 随后才被声明为这个载体类型上的 `Set α`。更准确地说，Lean 中的 `Set α` 是以 `α` 为定义域的谓词；`Type*` 及其宇宙（universe）层级则提供比集合更抽象、更通用的类型论组织方式。这种设计让同一套定理可以在任意载体类型上复用，也是 Lean 表达力与可组合性的重要来源。

Litex 选择了另一种任务边界。因为它直接以集合论对象和成员关系作为语言表层，语言与内核可以针对集合、成员、子集、交集和并集等高频集合论知识提供专门的语法与验证路径。在这个任务上，用户只需用集合类型关键字 `set` 声明三个集合和预期的包含关系，代码因而更接近日常集合论书写，也明显更简洁。

这里的差异不应简化成“短代码一定比长代码强”。Lean 也可以用更短的证明对象或自动化证明同一命题；上面的版本刻意保留《Mathematics in Lean》中展开定义、拆开交集成员再重新组合的教学路径。真正的对比是默认接口：Lean 先给集合一个类型论载体，再由用户或证明指令构造证明；Litex 则把常见集合论关系直接做成语言可以识别和检查的数学事实。

这种集合论式表面并不表示 Litex 没有约束。函数参数的定义域、返回集合、结构字段和集合成员关系仍然需要通过良定义性检查；只是这些约束尽量写在数学家本来就会写的位置。Litex 也保留参数化构造关键字 `template`，因为普通数学确实需要按载体、参数或假设索引的对象族；Litex 并不把自己描述成完整的依赖类型论。

更关键的是，Litex 不要求作者在每次使用函数时重复书写这些良定义性条件的传递过程。一旦函数拥有经过检查的契约——参数定义域、返回集合以及调用所需条件——这个契约就成为函数数学接口中可以复用的一部分。调用函数时，验证器会检查实参是否满足参数定义域，推出返回对象属于返回集合，并在嵌套调用中继续传递这些事实。良定义性的证明责任并没有消失；从源码中省去的，是作者对这条传递链的反复书写。这与普通数学实践一致：在 `f : A → B`、`g : B → C` 和 `a ∈ A` 已经成立之后，人们会直接写 `g(f(a))`，而不会重新写一遍 `a ∈ A ⇒ f(a) ∈ B ⇒ g(f(a)) ∈ C`。

同样的选择也会延伸到群这样的数学结构：结构仍然必须有载体，运算仍然必须说明输入和输出落在哪里；区别在于，Lean 的默认接口首先以类型和函数呈现这些约束，Litex 则首先以集合、成员关系和集合上的运算呈现它们。

正因为这些约束仍然以数学家熟悉的对象和关系呈现，集合论式表面的意义不只在于代码更短，也在于让形式陈述保持可审核。

<details>
<summary><strong>AI 生成数学中的规格对齐</strong></summary>

证明助手可以回答一个精确的形式问题：这份证明是否证明了实际编码进系统的命题？但仅靠内核检查，它不能回答另一个问题：这个被编码的命题，是否正是作者原本想表达的数学？AI 生成的形式产物可能在内部完全正确，却只形式化了一个特例，改变了原定义或论域，弱化了预期结论，甚至只是在一个看似正确的定理名下证明了另一件事。这不是逻辑健全性的失败，而是数学意图与形式规格没有对齐。

AI 能力变强，并不会消除对照数学意图与形式规格的必要性。作者或其他负责任的审核者仍然需要能够读懂形式陈述，并从中认出原本的数学意图。Lean 专家当然可以完成这种审核，但 Lean 的类型论抽象、细化、类型类、库接口和证明机制，可能使提出原始命题的数学家或领域专家难以直接审核生成物。如果真正对数学负责的人无法理解它的形式表达，内核接受就可能只是让人对错误的命题产生信心。

Litex 的集合论式表面，目的正是缩小这一语义距离。集合、成员关系、定义域、条件、中间事实和结论，尽可能以更接近日常数学书写的形式保留在源码中，同时又具有精确、可由机器检查的含义。Litex 不能自动保证作者或 AI 选择了正确的定义和定理，但它希望让这一选择能被真正理解数学的人直接审查，而不是只能由证明助手专家解读。

可读性在验证之后同样重要。当一批形式化文本仍然清楚暴露它们的数学对象和事实时，人类才能比较、批评和重新组织它们，从中看到反复出现的结构，进一步发现更好的抽象、新的猜想或新的数学视角。如果形式化产物在人眼中只剩下一层层实现机制，这种理解和发现数学的机会也会被大大削弱。

**因此，这里期望的责任分工是：AI 可以生成形式化，内核负责核验生成物是否证明了它在形式上声称的命题，而人类仍然必须能够确认这个命题正是自己想表达的数学。Litex 把这最后一步视为语言设计的核心要求。**

</details>

> **设计空间中的位置。** 集合论式的表述并非 Litex 首创：
> [Mizar 的数学库](https://wiki.mizar.org/library/) 基于塔斯基–格罗滕迪克（Tarski–Grothendieck）集合论；
> [Lean](https://lean-lang.org/doc/reference/latest/The-Type-System/) 和
> [Rocq](https://rocq-prover.org/doc/V9.2.0/refman/language/core/index.html) 向用户展示依赖类型论内核；
> [Isabelle/HOL](https://isabelle.in.tum.de/website-Isabelle2024/dist/library/Doc/Isar_Ref/HOL_Specific.html)
> 使用多态高阶逻辑。
>
> 在命题层面，Litex 面向用户的语言大体具有一阶逻辑的风格。事实从数学对象之间的原子关系或对具名谓词的调用开始，再通过一组刻意受限的经典逻辑形式和量词加以组织。这里“受限”很重要：Litex 倾向于采用规范化的事实形态，而不是让公式任意递归组合；命题和证明也不能像普通对象那样作为一等值任意传递和组合。这描述的是命题接口，并不意味着验证器只是一个通用的一阶定理证明器：它还会检查良定义性，并在定义、当前上下文以及受支持的内置规则和推理规则中寻找验证依据。
>
> 在这个背景下，Litex 的问题更具体地落在面向用户的对象接口上：
> 一套小型、以成员关系为中心的集合论式表层，能否在不要求用户先管理类型
> 宇宙（universe）的前提下，覆盖有实质内容的数学？

### 从群的两种定义模式，看如何从头搭建一个数学理论

Litex 选择集合论，一个重要意义不只是让集合、成员关系和函数保持日常数学的样子，也在于为不同数学理论提供一套小而统一的共同起点。集合、函数、关系和运算本来就是分析、抽象代数和线性代数教材中的常用语言；从它们出发，一个领域的定义和定理可以主要沿着自身的数学依赖逐层生长，而不必先服从某个大型外部库对该领域的既有编码。这里把这种能力称为**数学理论的自举**，或者**自包含的理论构建**。

外部库可以提供可复用的成果、缩短建设过程，却不应决定哪些数学能够被表达和推演。下面的群定义例子足够小，可以把这种取舍展示清楚：两个片段表达同一种熟悉的数学结构和同一个单位元唯一性结论，但对“载体是什么”“二元运算是什么”以及“结构规律如何进入后续证明”给出了不同的默认接口。

#### Lean：`Type` 上的记录类型（record）与柯里化函数

```lean
structure Group where
  Carrier : Type
  mul : Carrier → Carrier → Carrier
  one : Carrier
  inv : Carrier → Carrier
  mul_assoc : ∀ a b c : Carrier, mul (mul a b) c = mul a (mul b c)
  one_mul : ∀ a : Carrier, mul one a = a
  mul_one : ∀ a : Carrier, mul a one = a
  mul_left_inv : ∀ a : Carrier, mul (inv a) a = one

theorem one_unique
    (G : Group)
    (e : G.Carrier)
    (hleft : ∀ a : G.Carrier, G.mul e a = a)
    (hright : ∀ a : G.Carrier, G.mul a e = a) :
    e = G.one := by
  calc
    e = G.mul G.one e := (G.one_mul e).symm
    _ = G.one := hright G.one
```

这段 Lean 记录类型首先要求 `Carrier : Type`：群的元素、运算和规律都依赖这个载体类型。二元运算 `Carrier → Carrier → Carrier` 按函数类型的结合方式表示 `Carrier → (Carrier → Carrier)`；结构规律则成为 `mul_assoc`、`one_mul` 等可投影的具名字段。这套函数式、类型论式接口具有很强的抽象与组合能力，也便于大型库精确复用；与此同时，作者需要接触宿主语言的函数构造和库的命名接口，并知道当前需要哪个定理变体与等式方向。上面的唯一性证明就显式写出了 `G.one_mul`。

#### Litex：集合上的运算与直接写下的结构事实

```litex
struct Group<s nonempty_set>:
    mul fn(x, y s) s
    one s
    inv fn(x s) s
    <=>:
        forall x, y, z s:
            mul(mul(x, y), z) = mul(x, mul(y, z))
        forall x s:
            mul(x, one) = x
            mul(one, x) = x
            mul(inv(x), x) = one

forall s nonempty_set, G &Group<s>, identity s:
    forall a s:
        G.mul(identity, a) = a
        G.mul(a, identity) = a
    =>:
        identity = G.mul(G.one, identity) = G.one
```

Litex 从绑定一个非空集合 `s` 开始，把群直接建模为这个集合上的结构。`mul fn(x, y s) s` 直接表示一个接收 `s` 中两个元素、返回 `s` 中元素的二元运算；结构规律则以普通数学事实写在 `<=>:` 中。用户可以从集合、运算、单位元、逆元和规律这些数学材料出发，亲手看着“群”逐层建立起来。单位元唯一性也直接写成 `identity = G.mul(G.one, identity) = G.one`，由内核寻找相应的单位律实例和等式方向。Litex 并不禁止命名；值得长期引用的定理和公共接口仍然可以写成具名定理 `thm`，但普通结构规律和局部事实不必为了被使用而逐条进入一套需要作者记忆的命名接口。

这种面向作者的简洁并不意味着结构规律会被无边界地自动释放；其释放规则仍然明确且可检查。

<details>
<summary><strong>实现说明：结构（`struct`）事实的释放边界</strong></summary>

`G.mul` 这样的字段路径依靠声明中写明的结构载体完成良定义性检查；检查字段路径本身不会把群公理加入上下文。上例中的直接绑定 `G &Group<s>` 会自动打开且只打开一层结构。对于函数返回值或值为结构的嵌套字段，作者需要写 `by struct def expression`：内核先验证该表达式属于声明所确定的结构，再只释放这一层。后来单独得到的 `expression $in &Group<s>` 保持不透明，既不能自行选择字段视图，也不能自行释放结构规律。

</details>

这段 Lean 代码本身也说明，Lean 当然可以不依赖 Mathlib 的既有群接口而自行定义群；真正的区别不是“能不能”，而是哪一种体验被设计成默认路径。对 Litex 追求的写作体验而言，集合论尤其合适，因为集合、成员关系、函数和关系构成了一套跨领域而又接近日常数学的共同语言。Litex 仍然依赖自己的内核、内置规则和标准库；这里所说的“从头搭建”，是让分析、抽象代数或线性代数的源码依赖主要反映理论本身的数学结构，让外部库成为可选的加速器，而不是表达能力的边界。

如果用户不必先说“我要调用 `one_mul`”，而可以直接写“这里应当等于什么”，那么源码的中心就不再是定理名和证明指令，而是数学事实本身。

## 2. 事实导向：从日常数学的工作流出发——定义、定理和证明

事实导向改变了源码与内核的分工：用户源码主要保存数学上应当成立的对象和事实，内核则负责寻找、检查并解释它们的局部依据。

Lean 是一种常用的证明助手和形式化语言，能够严格检查人类和 AI 写出的形式化证明。它的默认交互以最终证明目标为起点：用户通过证明指令持续改写、分解或关闭当前目标，系统据此构造证明对象，再交给内核检查。

> **Lean 证明指令：定理先给出最终证明目标 → 用户声明应当如何改写、分解或关闭它 → 信息视图显示还剩哪些证明目标 → 证明指令构造证明对象 → 内核检查该证明对象。**

下面以这样一个例子开始：先定义序列收敛，再根据该定义证明——如果序列 `{s(n)}` 收敛到实数 `a`，那么序列 `{c * s(n)}` 收敛到实数 `c * a`。

```lean
import Mathlib

def ConvergesTo (s : ℕ → ℝ) (a : ℝ) :=
  ∀ ε > 0, ∃ N, ∀ n ≥ N, |s n - a| < ε

theorem convergesTo_const (a : ℝ) : ConvergesTo (fun _x : ℕ ↦ a) a := by
  intro ε εpos
  use 0
  intro n nge
  rw [sub_self, abs_zero]
  apply εpos

theorem convergesTo_mul_const {s : ℕ → ℝ} {a : ℝ} (c : ℝ)
    (cs : ConvergesTo s a) :
    ConvergesTo (fun n ↦ c * s n) (c * a) := by
  by_cases h : c = 0
  · convert convergesTo_const 0
    · rw [h]
      ring
    rw [h]
    ring
  have acpos : 0 < |c| := abs_pos.mpr h
  intro ε εpos
  dsimp
  have εcpos : 0 < ε / |c| := by
    exact div_pos εpos acpos
  rcases cs (ε / |c|) εcpos with ⟨Ns, hs⟩
  use Ns
  intro n ngt
  calc
    |c * s n - c * a| = |c| * |s n - a| := by
      rw [← abs_mul, mul_sub]
    _ < |c| * (ε / |c|) :=
      mul_lt_mul_of_pos_left (hs n ngt) acpos
    _ = ε := mul_div_cancel₀ _ (ne_of_lt acpos).symm
```

上面的 Lean 证明展示了一种高度通用、抽象且可组合的模式，这种模式是 Lean 强大表达能力的重要来源。不过，它的默认推进方向与日常数学书写并不完全相同；初学者还需要熟悉相当数量的证明指令关键词。相比之下，日常数学书写更常按下面的顺序推进：

1. 写下对象、定义和条件；
2. 看到一个熟悉的模式；
3. 使用已经知道的事实、定义或计算，写出下一条事实；
4. 让这条事实成为后续推理的上下文。

Litex 把这种日常数学工作流变成它默认的运行逻辑。聚焦到事实导向这一层，可以概括为：

> **Litex：用户声明“什么应当成立” → 检查器寻找证明依据 → 通过的事实扩展当前上下文。**

仍以这个序列问题为例，对应的 Litex 代码读起来更接近日常数学表达：

```litex
prop is_eventually_close(s fn(n N) R, a R, epsilon R+, N0 N):
    forall n N:
        n >= N0
        =>:
            abs(s(n) - a) < epsilon

prop converges_to(s fn(n N) R, a R):
    forall epsilon R+:
        exist N0 N st {$is_eventually_close(s, a, epsilon, N0)}

thm converges_to_mul_const:
    ? forall s fn(n N) R, a, c R:
        $converges_to(s, a)
        =>:
            $converges_to(fn(n N) R {c * s(n)}, c * a)
    claim:
        ? forall epsilon R+:
            exist N0 N st {$is_eventually_close(fn(n N) R {c * s(n)}, c * a, epsilon, N0)}
        abs(c) + 1 > 0
        epsilon / (abs(c) + 1) $in R+
        obtain N0 from exist K N st {$is_eventually_close(s, a, epsilon / (abs(c) + 1), K)}
        witness exist K N st {$is_eventually_close(fn(n N) R {c * s(n)}, c * a, epsilon, K)} from N0:
            forall n N:
                n >= N0
                =>:
                    abs(s(n) - a) < epsilon / (abs(c) + 1)
                    abs(c * s(n) - c * a) = abs(c * (s(n) - a)) = abs(c) * abs(s(n) - a)
                    abs(c) * abs(s(n) - a) <= (abs(c) + 1) * abs(s(n) - a) < (abs(c) + 1) * (epsilon / (abs(c) + 1)) = epsilon
                    abs(fn(k N) R {c * s(k)}(n) - c * a) < epsilon
            by def $is_eventually_close(fn(n N) R {c * s(n)}, c * a, epsilon, N0)
    by def $converges_to(fn(n N) R {c * s(n)}, c * a)
```

<a id="goal-1"></a>
### 为什么普通事实不需要名字，也不需要证明指令？

收敛例子里，`abs(c) + 1 > 0`、`epsilon / (abs(c) + 1) $in R+` 和一连串不等式都没有名字。用户也没有逐行写“调用哪个证明指令、使用哪个库定理、朝哪个方向改写”；用户直接写下自己要得到的数学事实，内核再寻找能够验证它的规则和上下文依据。

> **事实导向最核心的人机分工是：用户写“我要证明什么”，Litex 寻找“这条事实可以怎样被验证”。**

具体来说，Litex 内核寻找能与结果匹配的证明依据，并解释找到的验证路径。Lean 的细化过程则按照用户的证明指令构造对应的证明对象，信息视图显示变化后的证明目标，内核检查该证明对象。

这并不表示 Litex 禁止命名。经典定理、标准库接口，或作者希望显式展示依赖时，仍然可以写具名的 Litex `thm`，用 `release thm` 释放全部结论，或用 `by thm ... => fact` 选择一个原子结论。

普通事实之所以不需要名字，也不需要显式调用证明指令，是因为 Litex 内核会根据事实的谓词、参数形状和当前上下文寻找验证路径。常见的验证来源包括内置或用户提供的全称事实，以及已知的具体事实和等式信息。Litex 还有更复杂的优化和策略，但它们不改变这个核心分工。

<details>
<summary><strong>展开：内核如何按事实形状寻找验证路径</strong></summary>

#### 1. 用内置规则匹配事实形状

一条原子事实（atomic fact）可以直观地拆成“谓词 + 参数”。如果借用自然语言的比喻，谓词像动词，参数像这个判断所谈论的名词。例如：

```text
a + b >= 0
```

它的关系谓词是 `>=`，两个参数是 `a + b` 和 `0`；参数内部还带有可继续观察的结构：左侧是两个对象的加法，右侧是零。内核不需要先知道这条事实叫什么名字，就可以根据这个事实形状缩小候选范围。

例如：

```litex
have a R = 1
have b R = 2

a + b >= 0
```

在这个局部上下文中，用户提交的目标就是最后一行 `a + b >= 0`。内核看到谓词 `>=`，再看到左参数的外层形状是加法、右参数是 `0`，于是尝试相应的非负性内置规则。Litex 内置了下面这条规则：

```text
forall x, y R:
    x >= 0
    y >= 0
    =>:
        x + y >= 0
```

目标结论与内置规则的结论匹配后得到 `x := a`、`y := b`；内核再回头检查实例化后的前提 `a $in R`、`a >= 0`（`1 >= 0`）、`b $in R`、`b >= 0`（`2 >= 0`），因而接受目标事实。

#### 2. 用用户提供的全称事实匹配

候选来源不只可以是内置规则。用户已经证明或明确假设的普通 `forall` 事实，也可以进入自动匹配：

```litex
abstract_prop p(x)

trust forall a R:
    $p(a)

$p(1)
```

面对目标 `$p(1)`，内核先按谓词 `p` 找到结论形如 `$p(a)` 的全称事实，再把参数 `a` 匹配为 `1`。这次实例化还要求 `1 $in R`；该条件能够通过检查，所以内核可以用这个全称事实验证 `$p(1)`。

注：`abstract_prop` 是 Litex 中“声明一个抽象谓词，但不提供定义”的语法形式。`trust` 是一种会产生警告的声明，表示这个事实不经验证就被接受。包含 `trust` 的成果不属于完全可检查的成果；它可用于明确标出外部假设或尚未消除的证明债务。

#### 3. 用具体事实（concrete fact）和已知等式匹配

第三类常见来源不是全称规则，而是已经存在的具体事实：

```litex
abstract_prop q(x)

forall a R:
    $q(a)
    a = 1
    =>:
        $q(1)
```

验证 `$q(1)` 时，内核找到同谓词的已知事实 `$q(a)`。两个参数虽然不是同一段文本，但上下文还知道 `a = 1`，所以它们在当前等式信息下能够匹配；`$q(a)` 因而可以被运输为 `$q(1)`。

</details>

### 小结：把“证明什么”写进源码，把“怎么证明”交给内核

这样的书写风格也和日常数学书写更接近：数学家通常不会在每条推理中显式写出“我将使用哪条定理、哪个等式、哪个定义”，而是直接写下“我想得到的结论”，读者再根据上下文和已知事实理解它为什么成立。

<details>
<summary><strong>个人观察：声明式与命令式的类比</strong></summary>

这里可以借用一个不完全精确的编程类比。声明式源码往往更强调“要得到什么”，命令式源码往往更强调“怎样得到它”。Litex 的事实导向风格更接近前者：用户声明“要证明什么”，内核寻找“怎么证明”。由于 Litex 会自动寻找让表达式良定义所需的条件，也会寻找当前事实成立的依据，作者通常不必先给普通事实命名，再在后文对应位置用 `by ...` 显式引用。这样既减少了显式依赖的传递，也让整门语言能够保持更小、更统一的表层语法。Lean 本身是函数式语言，但其证明指令工作流在交互感受上可以更接近命令式：源码逐步描述如何变换当前证明状态。这只是对交互风格的类比，不是对编程语言的严格分类。

</details>

> **设计空间中的位置。** 寻找局部证明依据并非 Litex 独有：
> [Lean `grind`](https://lean-lang.org/doc/reference/latest/The--grind--tactic/)、
> [Rocq `auto`](https://rocq-prover.org/doc/master/refman/proofs/automatic-tactics/auto.html)
> 和 [Isabelle/Isar](https://isabelle.in.tum.de/doc/isar-ref.pdf) 通过显式证明指令（tactic）或
> 证明方法（proof method）提供局部自动化；[Mizar](https://mizar.uwb.edu.pl/project/mizman.pdf)
> 有空验证（empty justification）；
> [ACL2](https://acl2.org/doc/index-seo.php?xkey=ACL2____DEFTHM) 可以在没有提示（hints）时
> 尝试证明定理事件（theorem event）；[Naproche](https://naproche.github.io/) 则用自动定理证明器
> 检查受控自然语言中的证明步骤。Litex 更具体的假设是：能否让普通数学陈述本身触发
> 局部验证（local justification），让验证只在当前上下文和受支持规则限定的范围内进行，
> 并在成功后把事实写回上下文、显示它的验证来源。

## 3. 自下而上构建证明流

Litex 以数学事实作为源码的基本单位。在一段证明中，这些事实并不是彼此孤立的：每条已经验证的事实都会扩展当前上下文，成为后续陈述可以使用的已知条件。随着新事实不断积累，证明流便从已有条件出发，向结论推进；这就是这里所说的“自下而上”。

按照这一设计，Litex 支持**声明式（declarative）的证明书写，其默认流程主要是前向推理（forward reasoning）**。它默认的推理单位是当前上下文中的下一条数学事实，而不是一个每行都必须立即推进的活跃证明目标。只要一条陈述位于当前作用域中、定义良好，并且能由现有上下文充分支持，内核就可以接受它、保存它、应用当前适用的推理规则，并把增强后的上下文交给后续陈述。几条数学分支也可以先分别生长，再由之后的陈述让它们汇合。

Lean 通常的交互式定理证明是以目标为中心（goal-directed）的，典型方向是向后、自上而下。最终定理先确定最终目标是什么；局部证明项（term）和证明指令再在这个预期之下进行细化，逐步把待完成的证明目标分解或反推为更简单的子目标，直到 Lean 能组装出完整的证明对象。

两者的默认问题可以概括为：Lean 问“怎么去化简当前的目标，让目标能化约成已知条件”；Litex 问“根据已知条件，下一条能够推出的事实是什么？”

> 可以把写证明想象成搭乐高：一开始，我们拿到一批可用积木，也知道最终成品应当是什么。Lean 证明指令的典型做法像从成品开始反向拆解，直到拆出的要求能够由手上的积木满足；Litex 的典型做法像从已有积木开始向前拼接，让一个个已经确认的局部结果最终汇聚成目标成品。这个比喻只说明默认推进方向，不表示 Litex 的验证标准更宽松，也不表示两种系统只能朝一个方向工作。

### 同一证明的两种推进方向：自上而下与自下而上

#### 例一：代数重写

这个局部重写例子展示同一条等式怎样沿两个方向展开。在 Lean 中，用户从待证明的目标出发，用每条 `rw` 指定接下来调用哪个事实、按哪个方向匹配和替换：

```lean
-- Using facts from the local context.
example (a b c d g f : ℝ) (h : a * b = c * d) (h' : g = f) :
    a * (b * g) = c * (d * f) := by
  rw [h']
  rw [← mul_assoc]
  rw [h]
  rw [mul_assoc]
```

对应的 Litex 写法把 Lean 从证明目标出发执行的四次重写，反过来写成一条等式链。这条等式链从目标的右端 `c * (d * f)` 出发，依次写出中间结果，最后到达目标的左端 `a * (b * g)`：

```litex
claim:
    ?forall a, b, c, d, g, f R:
        a * b = c * d
        g = f
        =>:
            a * (b * g) = c * (d * f)
    c * (d * f) = (c * d) * f = (a * b) * f = a * (b * f) = a * (b * g)
```

1. 第一个等号对应 `rw [mul_assoc]`。
2. 第二个等号对应 `rw [h]`。
3. 第三个等号对应 `rw [← mul_assoc]`。
4. 第四个等号对应 `rw [h']`。

这四个等号与 Lean 的四条 `rw` 恰好逆序对应。Lean 的代码告诉系统“下一步调用哪个事实、朝哪个方向改写证明目标”；Litex 的代码则告诉系统“如果这些推理能够完成，关键的中间结果应当是什么”。内核再从当前上下文、等式匹配和结构规则中寻找每个相邻等式的依据。

对人类和 AI 而言，自下而上的价值还在于可积累性：一串分别提交并通过验证的陈述可以成为已验证前缀，下一条 `unknown` 则标出当前需要修正的位置。未完成尝试中已经接受的部分仍可检查、复用和继续推进；不过，一个内部结论失败的复合语句不会因此被部分写入环境。

理解这种工作流，还需要同时看到三件事：它与 Lean 默认交互方向的差异、Litex 为自动验证承担的可信成本，以及它在已有系统中的位置。

> **说得尖锐一点：对于更习惯从条件向前推导的作者，Lean 常见的证明指令工作流有时会像从最后一页开始读一本数学书、从最后一页开始写一篇论文——先固定最终证明目标，再向后反推前面必须补出什么。**

> **另一方面，从第一性原理看，Litex 当前最大的问题，是它的可信内核太大。Litex 把数百条常见证明模式放进内置规则（builtin rules）和推理规则（infer rules），把工作从用户的证明脚本（proof script）移进了可信计算基。证明工作并没有消失，只是被系统吸收了。要让 Litex 的验证结果再由可信边界更小且相对独立的 Lean 内核复核，Litex 还需要把记录的验证路径编译成 Lean 证明对象；这一编译覆盖是可行的，但需要时间打磨。**

> **设计空间中的位置。** Mizar 和 Isar 已经支持向前展开的声明式证明文本，ACL2 会累积
> 可复用的定理数据库，Naproche 会逐步检查数学陈述。因此，“自下而上生长”本身并不是
> Litex 的差异化主张。Litex 真正检验的是这样一套组合：普通事实（fact）提交后会触发验证，
> 并在成功后扩展上下文；局部验证（local justification）不需要另行调用证明方法（proof method）就会启动；
> 只有常规自动验证不足时，作者才需要写出显式证明结构。

要让这套更大的验证机制获得独立复核，Litex 必须把记录下来的验证路径交给更小的 Lean 内核检查。

## 4. 和 Lean 兼容：通向 Lean 可信生态的简洁数学前端语言

Litex 首先是一门可以独立工作的形式化语言。它拥有自己的语法、运行时和内核。一份 Litex 数学文档即使不编译成 Lean，也能直接接受 Litex 的良定义性检查、事实验证和局部证明反馈。因此，这里的“Lean 数学前端语言”说的是：Litex-to-Lean 编译器会把当前已经支持的验证路径翻译成 Lean 证明对象，并以逐步扩大覆盖面的方式连接 Lean 生态。*我期望 Litex 的发展可以为 Lean 社区提供新的形式化数学内容和接口经验，Lean 的内核与 Mathlib 生态也能反过来帮助 Litex。两者的关系不是竞争，而是互补。*

事实优先（fact-first）的小步验证让人和 AI 可以把注意力放在数学对象、条件、中间事实和结论上，并从 Litex 内核获得快速、局部而可追踪的验证反馈。相比之下，细化、类型类、命名空间和证明指令调用等机制，是 Lean 作为通用编程语言获得表达力与可组合性的重要来源。

*编译器又让这种互补关系多了第二层作用：为 Litex 的严谨性提供重要的独立保障。* 当前 Litex 仅 `src/` 下的 Rust 源码就接近 20 万行，并且随着数百条内置规则、推理规则和新能力持续增长；审核如此大的可信实现面，天然比审核规模小得多的 Lean 内核更困难。当一条 Litex 验证路径能够被完整编译为 Lean 证明并由 Lean 内核接受时，就为这条已覆盖路径提供了强而独立的正确性证据，显著降低了对 Litex 自身大型实现的单一依赖。

_这仍然是 Litex 正在实现和检验的目标，而不是当前测试版已经全面达成的能力。现阶段的 Litex-to-Lean 编译器仅覆盖部分验证路径。编译器的基本思路和框架已经建立，但细节上仍需进一步完善。我欢迎社区的反馈和贡献。_

<details>
<summary><strong>Litex 到 Lean 的编译器如何工作</strong></summary>

生态复用和独立复核这两层作用，共同指向一条自然的技术路线。Litex 基于集合论，Lean 的 Mathlib 也对集合论数学有丰富支持。Litex 的验证机制省去了用户手写许多证明构造步骤的工作，但验证器会保留它所使用的路径。原则上，每个已支持且已记录的验证步骤都可以由相应的 Lean 定理或证明构造来表示，再组装成证明对象。这就是 Litex-to-Lean 编译器在架构上顺理成章的原因。

把这条路线落到实处，就需要在 Litex 与 Lean/Mathlib 之间建立映射。在验证层，编译器把已支持的 Litex 验证路径映射为相应的 Lean 证明构造；在数学对象层，它通过经过设计的包装层（wrapper）把 Litex 对象映射到 Lean 表示，而不是做机械的直译。这种映射可行，但需要时间开发和验证。中介代码位于 https://github.com/litexlang/golitex/blob/main/lean/Litex/Core.lean，并仍在持续完善。

可执行的 [Litex-to-Lean-to-Mathlib pipeline](../showcases/litex_to_lean_mathlib_pipeline/README.md) 展示了具体的 Rust 调用链、内核边界保留的递归 `StmtResult` 证据、生成的 Lean 证明、单独的外部 adapter，以及消费该 adapter 的 Mathlib 下游文件。蓝图只保留稳定架构；实现级源码导航和可运行门禁由该 showcase 维护。

一条简单的数值定理可以同时说明保留证据的映射与面向生态的公开接口。例如下面这条已经由 Litex 验证的定理：

```litex
thm litex_real_add_comm:
    ? forall a, b R:
        a + b = b + a
```

这个例子区分了两层 Lean 接口。第一层是编译器的规范定理（canonical theorem），它保留 Litex 分类和验证证据：

```text
∀ {α β : Type} (a : α) (ha : Litex.In a Litex.R)
  (b : β) (hb : Litex.In b Litex.R),
  Litex.Same
    ((Litex.In.rep a ha : ℝ) + (Litex.In.rep b hb : ℝ))
    ((Litex.In.rep b hb : ℝ) + (Litex.In.rep a ha : ℝ))
```

编译器到这条由源码拥有的声明为止，不再额外发明下面这个普通 Lean 推论：

```text
theorem litex_real_add_comm (a b : ℝ) : a + b = b + a
```

因为 `.lit` 文件中并没有这条声明。这个“只翻译源码声明”的边界使生成的
Lean 可以审核：定理名、定理陈述和证明路径都必须追溯到源码拥有的事实。

如果需要普通的 Mathlib 接口，就由外部 AI 或人类在单独的、非生成 Lean
模块中编写。这个 adapter 可以导入并检查生成模块，但新增陈述及其 Lean
证明由 adapter 自己负责。编译器不会把 API 设计或新的目标语言数学藏在翻译中。

**因此互操作性对应两个明确分开的产物：ToLean 提供 Litex 源码的可由内核
检查的翻译；外部 adapter 提供任何新增的 Lean/Mathlib 接口。Lean 用户可以
导入 adapter，同时不会把它误认为编译器输出。**

这个例子也刚好暴露了编译器必须解决的两个底层问题。第一个是理论问题：如何在 Lean 和 Mathlib 中表示 Litex 的数学。同一个数学对象或语句往往有多种表达相同数学含义的 Lean 写法，而具体选择会长期影响生成代码能否自然复用 Mathlib、Litex 后续功能如何扩展，以及 Litex 与 Lean 两个生态如何协作。因此，函数、集合、成员关系和良定义性等基础概念需要一套一致且可持续的表示方式，而不只是让眼前的示例通过。

第二个是实践问题：如何把 Litex 内核成功执行时产生的信息变成 Lean 证明。Litex 验证会沿一棵搜索树把目标拆成更小的子目标；成功分支必须把所用规则、事实、数学对象、各子目标的证明和良定义性结果，以结构化信息从叶子返回根节点。语句执行中产生的声明、对象、事实和作用域变化也需要一并保留，使编译器能够确定性地重放 Litex 已经找到的验证路径，而不是从显示文本重建证明，或让 Lean 另行搜索证明。

</details>

因此，Litex 与 Lean 的连接不是让一方取代另一方，而是让 Litex 承担面向数学的写作接口，让 Lean 提供小内核复核与生态复用。对于编译器已经覆盖的路径，这两层能力可以连成同一条可验证、可审核、可复用的工作流。

## 从语言到生态：Litex 想扮演什么角色

**Litex 面向人类与 AI，既是可读推理的前端，也是可信推理数据的生产层，并通过 Lean/Mathlib 接入现有形式化数学生态。它希望让形式化语言不仅服务于数学与证明助手专家，也成为 AI、工程和其他领域实践者检查、组织与推进可信推理的工具。**

这三个角色分别对应以下具体产物：

| 生态角色 | Litex 希望产生的实际成果 |
| --- | --- |
| 可读推理的前端 | 人可以直接审核的数学对象、条件、中间事实和结论 |
| 可信推理数据的生产层 | 经过机器检查的事实与验证来源、明确的停止边界，以及被显式标出的 `trust` 与其他可信边界 |
| 现有生态的接入层 | 当前已支持源码路径对应的 Lean 证明对象，以及明确分离、由 AI 或人类编写的新增 Lean/Mathlib adapter |

这里的“可信推理数据”不是说所有 Litex 输出已经拥有成熟证明助手同等级别的可信保证。它首先表示数据携带机器检查结果、验证来源和明确边界；Litex 自身的内置规则、推理规则、`trust` 和实现仍属于必须审计的可信面。只有在一条验证路径被完整编译并由 Lean 内核接受时，这条已覆盖路径才额外获得较小且相对独立的内核复核。当前编译覆盖和独立 adapter 生态都仍在扩展中。

因此，Litex 代码和数据集的数量只是中间指标。真正重要的是这些产物能否被人读懂、被机器检查、被后续推理复用，并在已经支持的范围内进入现有形式化数学工具链；也只有这样，Litex 才可能从一种语言实验逐渐成为数学、AI、工程和其他领域可以共同使用的推理基础设施。

<a id="conclusions"></a>

## 总结

Litex 的目标是让形式化数学的书写和验证更接近日常数学思维。通过提供一套更接近数学家日常书写的语法和交互契约，Litex 试图降低形式化书写与审查的门槛，让数学文本变得可执行，并促进更深的数学理解和发现。

这里可以作一个类比：编程语言会不断建立新的抽象层。C 通常让程序员不必逐条安排汇编指令；Python 等更高层语言又吸收了更多常规工作，包括大量手动内存管理，以及为大多数变量预先声明类型的要求。

在这个意义上，Litex 通过数百条常见内置规则，以及按事实形状进行的匹配和替换，尝试为常规证明衔接工作建立一层抽象。Litex 的验证机制、它向用户暴露的数学对象与语句，以及它刻意隐藏的实现细节，都服务于同一项取舍：让源码尽量停留在数学思维实际发生的层级。Lean 提供更通用的抽象、小型内核和成熟生态；Litex 则尝试提供更贴近日常数学的专用接口。对于编译器已经覆盖的验证路径，Lean 还可以提供独立复核。

<details>
<summary><strong>个人类比：从汇编地址到事实标识符</strong></summary>

C 之所以比直接书写汇编更容易使用，不只是因为语法更短。汇编最终仍然需要地址、标签和跳转目标，但 C 程序员通常不必亲自记住某段代码位于哪个地址，也不必手工维护每一次引用指向哪里；编译器会根据源码中的变量、函数和控制流，建立并维护它们与底层位置之间的对应关系。

C 可以编译成汇编；在当前已覆盖的验证路径上，Litex 可以编译成 Lean。为了让生成的 Lean 证明精确复用已经验证的事实，Litex 的运行时、验证证据和编译器内部仍然必须保留 `FactId`。验证时，Litex 内核根据事实形状和当前上下文寻找依据，并把选中的引用以 `FactId` 记录在验证路径中；编译到 Lean 时，编译器不会重新猜测依赖关系，而是把这个 `FactId` 精确解析为对应的局部假设或生成定理。

普通 Litex 用户因此不必为了使用一条刚刚得到的事实，先给它起名、记住它的内部标识符（ID），再在后文手工写出这个标识符。这个类比并不是说地址或 `FactId` 消失了，而是说高层语言把标识符之间可机械维护的对应关系交给了系统：**C 让程序员不必直接管理汇编地址；Litex 让数学作者不必直接管理普通推理中的事实标识符。** Litex 中值得长期引用的公共定理仍然可以命名并直接调用；不再强制的是为每一条普通事实命名。

</details>

随着人类与 AI 的协作逐步创造和积累更多数学知识，形式化系统也应当探索不止一种书写和验证这些知识的方式。仅从默认交互方向来看，Litex 在有限意义上可以被看作“相反的 Lean”。这条设计路线不是要取代 Lean，而是为人和 AI 如何编写形式化数学代码，提供另一条值得实践和检验的思路。

**Litex 的成功，不在于写了多少 Litex 代码，而在于它能否把可读推理转化为可用的、可兼容到现有形式化语言系统的成果，并真正服务于数学、AI、工程和其他领域。**

这意味着评价 Litex 时，应当观察的是结果而不只是产量：人能否直接阅读并审核数学意图；人和 AI 能否利用验证依据和停止边界继续推进；已经检查的事实能否跨文件、项目和数据集复用；当前支持的验证路径能否进入 Lean/Mathlib 并获得独立复核；这些产物是否真的被数学、AI、工程或其他领域的任务采用。代码量、定理数和数据集规模可以记录进展，却不能单独证明上述目标已经实现。

如果这条路线成立，它首先会降低形式化书写与审查的门槛，然后让可读数学文本同时成为可检查、可复用的成果，并进一步帮助人类和 AI 更系统地理解数学对象、定义、定理和证明之间的关系。更深的数学理解与发现是这一过程可能带来的长期结果，而不是仅凭语言设计就已经达成的结论。
