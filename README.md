# Litex

### A formal language where mathematics verifies itself

Created and maintained by Jiachen Shen.

[Website](https://litexlang.com) · [Blueprint](docs/Litex_Blueprint.md) · [中文蓝图](docs/Litex中文蓝图.md) · [Manual](docs/Manual.md) · [Cheat Sheet](docs/cheatsheet.md) · [Install](docs/setup.md) · [Examples](examples/README.md) · [Zulip](https://litex.zulipchat.com/join/c4e7foogy6paz2sghjnbujov/)

Litex is a set-theoretic, fact-oriented formal language that builds proof flows
from the bottom up and is compatible with Lean. It lets humans and AI write
mathematical facts directly and see why verification succeeds or where it stops.

> **Litex is an experimental hobby project in beta; expect rough edges.**

## Why Litex?

AI is rapidly lowering the cost of producing arguments, proofs, and scientific
hypotheses. But answers that *look right* are not automatically reliable
knowledge. Candidate reasoning is outgrowing our ability to check it. This is
**reasoning overflow and validation crisis**.

Litex studies how checkable knowledge should be represented and constructed
step by step. It tests whether facts as the basic unit, with immediate checking
and local rollback as the interaction mechanism, can form a new design paradigm
for formal languages. It further asks how this paradigm changes the cost for
humans and AI to construct, understand, audit, repair, and reuse checkable
knowledge. If supported, the hypothesis could lower the barrier to using formal
languages and help rigorous verification capacity keep pace with the growth of
candidate reasoning in the AI era.

Correctness is only half of this crisis. Mathematics also pays a
**complexity tax on understanding**. Long proofs, distant representations, and
steep tools can make verified results hard to explain or reuse. Some difficulty
is mathematical. Some is added by the formal interface. We rarely ask how to
reduce the latter.

Terence Tao's [2026 ICM lecture](https://teorth.github.io/tao-web/slides/age-of-ai-icm-2026.pdf)
shows how proof generation and verification can outpace exposition, digestion,
and canonicalization. This context motivates Litex's question but does not
answer it; the representation-and-interaction hypothesis above is Litex's own.

Formalization cannot remain a specialist-only practice. Domain experts should
be able to express, check, repair, and review formal reasoning—including work
generated by AI.

**Litex tests that path.** It is a set-theoretic, fact-oriented, bottom-up
formal language with a growing Lean-compatible checking path. It aims to lower
the barrier to rigor, not the standard of rigor.

## Two barriers between mathematics and formalization

The next two examples show two sources of this tax. Both are trivial for Lean.
The comparison concerns first-contact interfaces, not mathematical power.

The first barrier is **entry knowledge**. A user may know a fact while still
needing to know imports, proposition syntax, types, and tactics before writing
it in a general proof assistant.

Litex:

```litex
1 + 1 = 2
```

Lean:

```lean
import Mathlib

example : (1 : ℝ) + 1 = 2 := by norm_num
```

The second barrier is **representation distance**. Even after learning the
tool, users may need to manipulate certificates and encodings that are not the
objects they ordinarily write. For a function on the positive reals, one
common Lean encoding packages the proof that an argument is positive:

```lean
example
    (f : {x : ℝ // x > 0} → ℝ)
    (x : ℝ) (hx : x > 0) :
    f ⟨x, hx⟩ = f ⟨x, hx⟩ := rfl
```

The corresponding Litex keeps the condition but leaves the application as
`f(x)`:

```litex
forall f fn(t R: t > 0) R, x R:
    x > 0
    =>:
        f(x) = f(x)
```

> **Users write mathematics; the system manages verification evidence.**
> Conditions cannot be omitted, but certificates need not always be threaded
> through source by hand.

This matters for AI review as well as convenience. A kernel can correctly
check the wrong proposition if an AI omitted a condition or changed a
quantifier. A readable formal statement lets the domain expert inspect whether
the checked proposition still matches the intended mathematics.

## The human–AI verification loop

Lowering the writing barrier is not enough. A formal system should also show
why it accepted a fact and where it could no longer continue.

```litex
forall A, B, c set, x A:
    A $subset B
    B $subset c
    =>:
        x $in B
        x $in c
```

Here `x $in A` and `A $subset B` support the first conclusion. Once accepted,
`x $in B` becomes part of the context that supports `x $in c`. Litex records
the facts and the verification routes it used.

If the source next asks for `x $in d` without any fact connecting `d` to the
other sets, Litex stops at that statement. `unknown` does not mean the
proposition is false; it means the current context and verifier have not
established it. A human or AI can then add a missing condition, split the
argument, or repair the formulation and continue from the boundary.

This loop—**write a fact, inspect its grounds or stopping point, retain valid
progress, and continue**—leads to four connected design choices.

## Four design choices

| Design choice | What it changes for the author |
| --- | --- |
| **Based on set theory** | Begin with sets, membership, functions on sets, and familiar mathematical structures. |
| **Fact-oriented** | Write the next fact that should hold; let the verifier search for local support. |
| **Bottom-up** | Let each accepted fact extend the context from which later facts can grow. |
| **Lean-compatible** | Compile currently supported verification routes into Lean proof terms for independent checking. |

### 1. Based on set theory: keep mathematical objects readable

Litex puts sets, membership, and relations between sets at its user-facing
surface. A set-theoretic statement can begin with sets rather than first
introducing a carrier type:

```litex
forall s, t, u set:
    s $subset t
    =>:
        intersect(s, u) $subset intersect(t, u)
```

This is a complete fact submitted to the verifier, not a proof hole. Litex
checks well-definedness and searches the relevant membership and subset rules.
The choice is an interface boundary, not a claim that type theory is
unnecessary; Lean's type-theoretic design provides powerful abstraction and a
mature ecosystem.

### 2. Fact-oriented: source preserves *what holds*

```litex
have a R = 1
have b R = 2

a + b >= 0
```

The last line has no theorem name and invokes no tactic. The verifier matches
the requested fact with supported rules and the current context, then accepts
it or reports where support is missing.

Stable interfaces can still be named as theorems, and explicit proof steps can
use definitions, witnesses, cases, contradiction, induction, or named results.
Fact orientation changes the default division of labor: source preserves
*what should hold*; the verifier searches for *how it can be justified*.

### 3. Bottom-up: let verified facts continue to grow

The set-inclusion example grows from `x $in A` to `x $in B` and then to
`x $in c`. This is Litex's default flow: derive a useful fact, keep it in
context, and continue forward.

Lean tactics commonly begin with the final Goal and reduce it backward toward
known hypotheses. Both systems can express both directions; the difference is
the default proof interface, not an exclusive capability boundary.

### 4. Lean-compatible: independently recheck covered paths

Litex has its own parser, runtime, verifier, builtin rules, and inference
rules. That makes it independently usable, but also gives it a larger trusted
implementation than a small proof-assistant kernel.

The Litex-to-Lean compiler translates supported recorded evidence into Lean
proof terms. Covered routes can then be checked by Lean; unsupported or trusted
routes fail instead of silently becoming `sorry` or hidden axioms. Coverage is
still partial. **"Every Litex file compiles to Lean" is a direction of work,
not a capability of the current beta.** See the [compiler README](lean/README.md)
for the implemented surface and current limits.

Litex is not trying to replace Lean. It tests a different hypothesis: that a
smaller, readable, fact-oriented interface can make checked mathematics cheap
enough for students, domain scientists, and AI agents to produce useful formal
data at scale.

## From design choices to mathematical practice

Mathematical work repeatedly alternates between two activities:
**definition** gives a domain its objects and reusable language;
**verification** establishes what follows from those definitions and the
available conditions.

```litex
prop is_unit_distance_from_two(t R):
    abs(t - 2) = 1

by def $is_unit_distance_from_two(3)
```

The `prop` introduces a mathematical concept. The next statement asks Litex to
unfold that definition and verify a concrete instance. Larger developments use
the same rhythm: define a small world, establish facts inside it, and reuse
those facts as the context grows.

## From Litex results to Lean and Mathlib

Independent checking and ecosystem reuse require two distinct artifacts:

1. **ToLean** compiles source-owned Litex declarations and supported evidence
   into canonical Lean theorems.
2. A separate human- or AI-authored **adapter** may import those generated
   theorems and expose new native Lean or Mathlib APIs.

Keeping these layers separate preserves ownership: the compiler does not
invent mathematics or public APIs that do not exist in the Litex source. The
[complete pipeline showcase](https://github.com/litexlang/golitex/tree/main/showcases/litex_to_lean_mathlib_pipeline/showcase2)
demonstrates the current path and its boundaries.

## From language to ecosystem

Litex aims to play three connected roles:

| Role | Intended output |
| --- | --- |
| Readable-reasoning front end | Inspectable objects, conditions, intermediate facts, and conclusions |
| Production layer for checked reasoning data | Verification sources, stopping boundaries, and explicit trust markers |
| Bridge to existing formal ecosystems | Lean proof terms for supported routes and separate adapters for additional APIs |

Real mathematics is the pressure test. Textbooks and datasets expose gaps in
the language, standard library, verifier, inference rules, diagnostics, and
proof organization. Successful translations can become examples or
benchmarks; failed translations should become explicit blocker evidence rather
than being hidden.

## What success means—and what it does not

A successful Litex run means that the current parser, runtime, verifier,
accepted rules, imported libraries, and mathematical context accepted the
statement. It does **not** mean the implementation is bug-free or has the audit
history of a mature proof assistant.

Read every result relative to its trusted background: builtin and inference
rules, imported interfaces, explicit `trust` and `axiom` assumptions, the
current implementation, and test coverage. `trust` and `axiom` are assumptions,
not checked derivations. A route compiled and accepted by Lean gains an
additional independent check for that covered path.

If formal languages become as routine as LaTeX over the next decade, their
entry cost should approach LaTeX's. This is a long-term standard, not a current
capability. It does not promise to make deep mathematics easy.

**Litex's success will not be measured by how much Litex code is written. It
will be measured by whether readable reasoning becomes checked, reviewable,
reusable results that genuinely serve mathematics, AI, engineering, and other
fields—and whether supported paths interoperate with existing formal systems.**

## Try Litex

The fastest route is the [online playground](https://litexlang.com). For a
local installation, see the short [setup guide](docs/setup.md). On
macOS and Linux with Homebrew:

```bash
brew install litexlang/tap/litex
litex -version
litex -e '1 = 1'
```

For more commands and JSON output details, use the complete
[CLI reference](docs/cli.md). Then continue with the
[examples](examples/README.md), the compact [cheat sheet](docs/cheatsheet.md),
or the full [manual](docs/Manual.md). The
[blueprint](docs/Litex_Blueprint.md) and [Chinese blueprint](docs/Litex中文蓝图.md)
give the complete design argument and comparisons.
